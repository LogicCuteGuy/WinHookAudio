# Windows audio constraints

Evidence checked 2026-09-09. Scope: expose devices and virtual cables to a DAW that performs processing/routing, with a custom ASIO interface and bridges for other clients. Existing-stream interception is excluded. Clocking, LAN, and GUI design belong to the main design work.

**Reported local evidence:** the main investigation observed VB-Matrix ASIO/cable registrations; live streaming was not verified. Registration does not establish working routes. The current deliverables are design artifacts and an interactive UI-only patchbay concept, not a built audio driver.

## KS access and the scope boundary

- **Evidence:** `KsCreatePin2` creates a new pin instance and returns its connection handle. The driver accepts compatible interface, medium, and format parameters. KS exposes pin factories and per-instance handles for streaming requests. [Microsoft: KsCreatePin2](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/ks/nf-ks-kscreatepin2), [KS pins](https://learn.microsoft.com/en-us/windows-hardware/drivers/stream/ks-pins).
- **Evidence:** pin factories have current/maximum instance counts. `KSPROPERTY_PIN_GLOBALCINSTANCES` reports driver-wide counts when supported; the property is optional. **Inference:** an enumerated KS device is not necessarily available to open concurrently; format support and instance/resource availability must be checked. [Microsoft: global pin instances](https://learn.microsoft.com/en-us/windows-hardware/drivers/stream/ksproperty-pin-globalcinstances).
- **Scope boundary / inference:** opening a pin supplies a new stream connection; it does not establish a supported way to seize or rewrite another application's already-open stream. No interception mechanism is required for this design. [Microsoft: KsCreatePin2](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/ks/nf-ks-kscreatepin2).

## WASAPI loopback: optional capture, not the cable foundation

- **Evidence:** endpoint loopback captures a rendering endpoint's mix. The loopback client must use shared mode; exclusive-mode streams cannot operate in loopback mode. Windows can copy the audio-engine output when no hardware loopback pin exists. Trusted drivers prevent capture of protected digital content. [Microsoft: loopback recording](https://learn.microsoft.com/en-us/windows/win32/coreaudio/loopback-recording).
- **Evidence:** process loopback can include a process and descendants, or exclude that tree. It is not bound to one physical endpoint and yields silence when the selected processes have no rendering streams. Microsoft's sample requires build 20348 or later; do not equate this with all Windows 10 releases. [Microsoft: ApplicationLoopback sample](https://github.com/microsoft/Windows-classic-samples/blob/main/Samples/ApplicationLoopback/README.md), [activation requirements](https://learn.microsoft.com/en-us/windows/win32/api/audioclientactivationparams/ns-audioclientactivationparams-audioclient_activation_params).
- **Inference:** these are capture facilities, not render/capture endpoint creation or rerouting facilities. They provide no general guarantee of capturing arbitrary native ASIO/KS paths; hardware/vendor loopback requires separate validation. Keep loopback optional for monitoring, outside the required device/cable exposure path. [Microsoft: loopback recording](https://learn.microsoft.com/en-us/windows/win32/coreaudio/loopback-recording).

## SYSVAD, a functional cable, and signing

- **Evidence:** SYSVAD demonstrates a WDM virtual audio driver using WaveRT and multiple devices. It does not implement audio mixing; capture and loopback are simulated with a generated tone, and some HLK tests are expected to fail. [Microsoft: SYSVAD README](https://github.com/microsoft/Windows-driver-samples/blob/main/audio/sysvad/README.md).
- **Proposal:** use SYSVAD only as a driver starting point if an owned cable is needed. Implement real render-to-capture sample transfer, buffering, format negotiation, stream lifecycle, and any required mixing. Exposing endpoints or passing the sample's visual meter check cannot prove that cable transfer works. [Basis: SYSVAD limitations](https://github.com/microsoft/Windows-driver-samples/blob/main/audio/sysvad/README.md).
- **Evidence:** modern production kernel-driver packages require Microsoft signing; legacy cross-signing is no longer accepted. Partner Center submissions require an associated valid EV certificate, although registered Authenticode certificates can sign submissions. [Microsoft: certificate policy](https://learn.microsoft.com/en-us/windows-hardware/drivers/install/deprecation-of-software-publisher-certificates-and-commercial-release-certificates), [signing requirements](https://learn.microsoft.com/en-us/windows-hardware/drivers/dashboard/code-signing-reqs).
- **Evidence:** Microsoft describes attestation signing as for testing, without HLK testing, on Windows 10 Desktop and later. It cannot publish drivers to Windows Update retail audiences; that route requires WHCP. Preproduction signatures require explicitly provisioned devices and are not trusted by default on retail systems. **Proposal:** budget production certification/signing separately from prototype development. [Microsoft: signing options](https://learn.microsoft.com/en-us/windows-hardware/drivers/dashboard/driver-signing-offerings).

## ASIO capabilities and official license choices

- **Evidence:** Steinberg offers ASIO development technology for recording/playback with multiple channels, variable bit depths and sample rates. **Proposal:** expose the router's selected devices/cables as DAW-facing ASIO channels; implement other-client bridging and simultaneous-client policy explicitly. SDK availability alone is not evidence of a completed aggregator or cable. [Steinberg: ASIO SDK](https://www.steinberg.net/developers/prorietary-sdk/).
- **Evidence:** capabilities depend on implementation: Steinberg's separate built-in ASIO driver permits one input device and one output device at a time and has a fixed buffer size. **Inference:** that product's limitations must not be treated as universal SDK limits or as proof of arbitrary aggregation support. [Steinberg: built-in driver](https://helpcenter.steinberg.de/hc/en-us/articles/17863730844946-Steinberg-built-in-ASIO-Driver-information-download).
- **Official choices, not legal advice:** Steinberg offers GPLv3 and a proprietary ASIO license side by side. Its GPLv3 FAQ describes switching products under GPLv3 terms, including source disclosure, while existing products may retain proprietary licensing. ASIO names/logos have separate trademark rules; GPLv3 does not cover their use. The proprietary portal supplies its agreement and SDK download. Select the applicable agreement before distributing SDK-derived work; this document makes no project-specific licensing determination. [Steinberg: open-source ASIO and FAQ](https://www.steinberg.net/developers/asiosdk-open/), [proprietary agreement portal](https://www.steinberg.net/developers/prorietary-sdk/).

**Validation still required:** device opens, cable sample transfer, supported formats/channels, and concurrent client behavior on the target system. No installation, streaming test, driver build, or system mutation was performed for this research.
