# 32-bit DAWs and Windows on ARM

Date: 2026-09-25
Status: accepted

## Context
The ASIO drivers were built for x64 only. An ASIO driver is a DLL loaded into the DAW, so it must
match the DAW's architecture: 32-bit DAWs (older hosts, 32-bit plug-in hosts) need a 32-bit DLL, and
on Windows on ARM an ARM64 DAW needs an ARM64 DLL while an x64 DAW (emulated) needs the x64 one. On
Windows on ARM both kinds of process read the same 64-bit registry view, so one CLSID has one
InprocServer32 path for both. Several processes of different bitness share the Slot Table, the Master
audio and the Bridge memory.

## Decision
- One architecture per build tree: `cmake -A x64 | Win32 | ARM64`. The DLLs are named by it:
  `WinHookAudio<Master|Bridge>ASIO64.dll`, `...ASIO32.dll`, `...ASIOARM64.dll`; `WHA_ARCH_X64 / X86 /
  ARM64` reach the code and the version resources. Same CLSIDs everywhere.
- 32-bit: registered in the 32-bit registry view (the installer's `HKLM32` entries; 32-bit
  `regsvr32` does the same). Nothing in the shared memory depends on pointer size: the Slot Table
  and the Bridge memory are `#pragma pack(1)` with fixed-width fields, the Virtual Cable IOCTL
  structs are `unsigned int` with `METHOD_BUFFERED`. The ASIO interface already matched the SDK on
  32-bit (methods `__thiscall`, callbacks `__cdecl`, `pack(4)`); only a size check assumed 64-bit
  pointers. `_BitScanForward64` became `std::countr_zero`.
- Windows on ARM: an ARM64X forwarder per DLL (`...ASIOARM64X.dll`, linked `/machine:arm64x` from two
  empty objects and two export tables): ARM64 callers are forwarded to `...ASIOARM64.dll`, x64 callers
  to `...ASIO64.dll`. The 64-bit registry entries point at it on ARM64. COM loads InprocServer32
  paths with `LOAD_WITH_ALTERED_SEARCH_PATH`, so the targets are found next to it.
- The Virtual Cable kernel driver stays x64 only: an ARM64 build needs the ARM64 compiler and an
  ARM64 PC in Test Mode to try it (many cannot turn Secure Boot off). On ARM64 the installer greys its
  choices out and skips it.
- Windows itself must be 64-bit (x64 or ARM64): Windows 11 has no 32-bit edition.
- CI: a `windows-11-arm` job builds ARM64 and runs the offline tests natively, builds the x64 DLLs
  there too and checks each forwarder from an ARM64 and an x64 process (`arm64x-test`); the x64 job
  also builds and tests 32-bit; one setup carries all three.

## Consequences
- Live on the dev VM (x64): the 32-bit Master through the 32-bit registry, like a 32-bit DAW: VB-Cable
  loop bit-exact in Exclusive (2 / 2), the one-app claim works across bitness; a 64-bit Master with a
  32-bit Bridge 1 client in another process: the Bridge ticks at 48000 Hz off the Master Clock and its
  -20 dBFS tone arrives on the Master input (peak 0.0997). Offline tests 16 / 16 as 32-bit.
- ARM64 is built and tested only by CI on GitHub's Windows on ARM runner: not on a real ARM64 PC with
  a DAW or audio hardware.
- The installer has not yet been run end to end with the new architectures.
